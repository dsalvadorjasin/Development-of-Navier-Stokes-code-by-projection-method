# Fortran 90 -> C++ port: how the port is organised and validated

The C++ code lives in `src/`, one `.cpp` per original `.f90` file, and is built
with `cpp.mk`. The original Fortran program is kept during the port as
the **reference oracle**: its outputs for both schemes are checked in under
`reference/upwind` and `reference/centred` (generated by
`tools/make_reference.sh`, which builds the Fortran code with the original
`Makefile` and runs it with `NS_DUMP_FIELDS=1`).

## Validating a single ported unit (hybrid build)

Every routine can be validated *in isolation*, before the rest of the code is
ported, by linking its C++ version into the Fortran program:

    make -f cpp.mk check-hybrid PORTED="timestep"

This builds `NS_lid_driven_cavity_hybrid` = Fortran `main` + all Fortran
routines **except** `timestep.f90`, which is replaced by `src/timestep.cpp`
(the `extern "C" void timestep_()` wrapper at the bottom of the file). The C++
globals of `variables.hpp` are aliases of the gfortran module variables
(`-DNS_HYBRID`, see `src/variables.cpp`), so the C++ routine reads and writes
the very same memory as the Fortran routines around it. The program is then run
for both schemes (`echo 1 | ...` and `echo 2 | ...`) and every output file is
compared with `reference/`:

| file(s)                                             | comparison                               |
|-----------------------------------------------------|------------------------------------------|
| `fields_*.txt` (u, v, p, u_star, v_star, rot, div)  | value by value, `|a-b| <= 1e-15 + 1e-12|b|` |
| `*.geo`, `*.vec`, `*.scl` (Ensight Gold binaries)   | byte for byte                            |
| `EnsightOutput.case`, `coordinates.txt`, `u_velocity.txt`, `v_velocity.txt`, `omega_boundary.txt`, `iccg2_iterations.txt` | exact text |

**Definition of done for a unit:** `make -f cpp.mk check-hybrid
PORTED="<unit>"` exits 0 for both schemes (prints `all files match the
reference` twice). Several units can be listed in `PORTED` to check them
together. A pure translation with the same operation order normally matches
the Fortran results *bit for bit* (both compilers target x86-64 SSE2 without
FMA and without value-unsafe optimisations); the small tolerance only
absorbs harmless differences such as a different association of a sum.

Whole-program check of the pure C++ executable (once every unit is ported):

    make -f cpp.mk check

## Translation rules

* **Arrays keep their Fortran index ranges.** Use the `FArray1`/`FArray2`
  views of `src/fortran_array.hpp`: `u(i,j)` in Fortran is `u(i,j)` in C++,
  with `u` declared `(0:nx+1,0:ny+1)` in both. Storage is column-major, so
  the ELL diagonal-offset arithmetic of `solver.f90` (`L(i-col,j)`,
  `coef(i+col,1)`, ...) can be transcribed literally; the linear index used
  by `matgen_cavity`/`calcul_2nd_membre`/`calcul_pressure_field`
  (`k = 1..ndim`, i fastest) is also unchanged.
  Compile with `CXXFLAGS+=-DNS_BOUNDS_CHECK` to catch out-of-range accesses.
* **Everything real is `double`.** The Fortran is compiled with
  `-fdefault-real-8`, so bare `real` (`xx`, `yy`) and default-real literals
  (`0.5`, `1.`, `2.`) are all double precision; `float(nx)` is
  `double(nx)`. Integer expressions stay integer (`2-u(i,ny)`,
  `(nx-1)/2` is integer division, `(i-0.5)*dx` is double).
* **Keep the exact operation order** of every arithmetic expression
  (`a**2` is `a*a`; `2./dx/dx` is `(2./dx)/dx`; do not factor or reassociate).
* **Loop variables are local.** The Fortran module makes `i, j, k, sum,
  a..h, u_tilde_*` global, but no routine depends on a value set by another
  routine, so declare them locally. Watch for a routine that depends on the
  value of a loop variable *after* its own loop finished: a Fortran
  `do j=2,ny ... end do` leaves `j = ny+1`. `calcul_new_velocity.f90` does
  exactly that (`u1(i,j)` in the top-wall loop reads `u1(i,ny+1)`); the port
  must reproduce it.
* **Fortran `do i=a,b`** executes for `i=a..b` inclusive (zero times if
  `a>b`); `do i=a,b,-1` counts down.
* **Formatted output must be reproduced byte for byte** (the text outputs are
  compared exactly), including quirks: `write(9,'(F1.5)')` cannot fit any
  value in one character, so gfortran prints a single `*` per line;
  `'(2I6)'`, `'(F6.3,a,F6.3)'`, `'(A,I6.6)'`, `'(i5)'` map to
  `%6d`, `%6.3f`, `%06d`, `%5d`; a Fortran record ends with `\n`; format
  `/` is an empty line. Free-format `write(*,*)` diagnostics on stdout are
  not compared, except that the ICCG2 iteration count must be printed as the
  **last token** of a line containing `Nombre` (converged) or
  `non convergence` (not converged) so that `iccg2_iterations.txt` can be
  extracted.
* **Ensight Gold binaries** (`ensight_cavity.f90`) are Fortran
  `unformatted, access='direct'` files with a single record: no record
  markers, just the payload, padded with zero bytes up to `recl`
  (gfortran pads direct-access records with NULs). Payload = 80-byte
  space-padded strings, 4-byte little-endian ints, and 4-byte floats
  (`real(sngl(x),4)` = `float(x)`), in the exact order of the `write`
  statement. Note `WriteEnsightVar` writes `VarFileName` (e.g.
  `velocity000200.vec`) as the first 80-byte string, and the omega call
  passes `jmin` where `kmin` is expected (harmless since both are 1, but
  keep the call as is). `.case` is a text file; reproduce it exactly
  (formats 10/15/25/45).

## Layout of a ported unit

    // C++ port of timestep.f90
    #include "routines.hpp"
    #include "variables.hpp"

    namespace ns {
    void timestep() { ... }          // body translated line by line
    }  // namespace ns

    #ifdef NS_HYBRID
    extern "C" void timestep_() { ns::timestep(); }   // already present in the stub
    #endif

Only the body of the stub function (which currently calls `not_ported(...)`)
needs to be written; the signature, the `extern "C"` wrapper and the
declaration in `src/routines.hpp` are already in place. Do not change
`variables.hpp`/`variables.cpp`/`cpp.mk` for a unit port.
